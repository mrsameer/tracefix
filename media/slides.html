The problem

3 a.m. Checkout is throwing 500s.
All you have is a stack trace.

step 1

Find the code

Map log paths like /srv/app/… to files in the repo.

step 2

Find the change

Which of this week's commits broke it?

step 3 · often skipped

Reproduce it

Write a test that fails the same way production did.

step 4

Fix it safely

Without breaking anything else, at 3 a.m.

Skipping the reproduction is why the same bugs come back. And "just ask an AI" is risky: who checks that its fix is actually right?

The solution

One command. Five verified outputs.

$ tracefix run prod_trace.txt --repo ./shopcart --id INC-4127
  • 01 Incident brief: every frame mapped to a repo file, with code context
  • 02 Suspect commit: git blame around the crash lines, ranked
  • 03 A regression test proven to fail exactly like production
  • 04 A fix proven to pass that test and keep the whole suite green
  • 05 An incident branch plus a report ready to use as the PR description

Feedback loop

A rejected first attempt was corrected automatically on retry.

Tests stay behind

Every incident adds a regression test to the suite.

Parallel agents

--agents N races Bob in isolated git worktrees.

Bob · reproduce bob#1 + bob#2 · separate worktrees, different strategies │ bob#2 › Writing file tests/test_tracefix_repro.py ✔ VERIFIED bob#2 attempt 1: KeyError raised from _stacked_rate() — matches production ■ bob#1 stopped — another agent already won (ACP session/cancel) Bob · fix ok in 19.2s (1 attempt(s), winner bob#2 of 2)

The first verified patch wins and is applied to the incident branch. Losing sessions are cancelled. More agents means more chances of a quick, correct answer, and the gates mean speed never costs correctness.
